Клиент на ZigZig client

Раздел на русском — исходный язык документации.This reference is in Russian. In brief: State of the Zig client, its commands, modules, design decisions, expected problems.

Теги: #Zig #клиент #Windows #GDIplus #подпись_URL

Собственная программа проекта: консольный клиент под Windows, который входит в аккаунт Ivideon, находит камеру Ivideon Cute 2 и показывает её изображение. Язык и цель выбраны пользователем: Zig 0.16, без сторонних библиотек.

12.2. Почему облако, а не USB или LAN

  • USB (проверено на машине пользователя): Cute 2 по USB не определяется никак — ни UVC-камера, ни сетевой адаптер RNDIS/ECM, ни COM-порт, ни диск; её нет и в истории USB-устройств Windows. Micro-USB у камеры — только питание.
  • LAN (проверка не завершена): скан локальной сети не удался — AmneziaVPN на ПК заворачивает 192.168.0.0/24 в туннель. Отдаёт ли прошивка RTSP/ONVIF/HTTP локально — неизвестно. В коде Android-приложения прямого обмена с камерой по LAN не найдено (см. 09-camera-attachment.md).
  • Облако: протокол восстановлен — этим путём идёт программа. Условие: камера привязана к аккаунту и в сети по Wi-Fi.

12.3. Команды (проект)

команда действие запрос API
ivideon login спрашивает email и пароль (пароль без эха; либо IVIDEON_EMAIL/IVIDEON_PASSWORD), сохраняет токен в .ivideon/token.json. Пароль не сохраняется POST /auth/oauth/token
ivideon cameras серверы и камеры: id, имя, online, модель, прошивка POST {api_host}/servers?op=FIND
ivideon snapshot [camera_id] [файл.jpg] один кадр в файл GET /cameras/{id}/live_preview (подписанный)
ivideon watch [camera_id] [--fps N] [--q 0..2] окно с «живой картинкой» из JPEG-превью тот же live_preview в цикле
ivideon url [camera_id] [--q 0..2] печатает подписанный URL живого видео для VLC/ffplay/mpv. URL содержит токен GET /cameras/{id}/live_stream
ivideon logout удаляет локальный файл токена (отзыв на сервере — POST /access_tokens/{id}?op=REVOKE — возможное улучшение, см. 03-auth.md) —

У всех команд планируется ключ --raw — печать ответа сервера с вырезанными секретами, для первой живой сверки протокола.

12.4. Модули

файл ответственность
src/main.zig разбор командной строки, диспетчер команд, человекочитаемые ошибки
src/api.zig HTTP через std.http.Client (TLS — реализация Zig std); конверт ответа; добавление access_token; повтор запроса после обновления токена
src/auth.zig OAuth-запрос (form-urlencoded + Basic base64("android-client:")), модель токена, чтение/запись .ivideon/token.json, refresh_token
src/sign.zig signedUrl() — сборка query в кодировке OkHttp, cseq, cs
src/viewer_win32.zig окно Win32; JPEG декодирует GDI+ (gdiplus.dll, поток из памяти — SHCreateMemStream из shlwapi.dll); перерисовка по таймеру; сеть в отдельном потоке

API sign.zig

const sign = @import("sign.zig");

const url = try sign.signedUrl(gpa, .{
    .base_url     = "https://eu01-api.ivideon.com",   // без завершающего '/'
    .path         = "/cameras/<id>/live_stream",
    .params       = &.{ .{ .name = "q", .value = "2" } },
    .access_token = token.access_token,
    .hmac_secret  = token.hmac_secret,                 // "" -> URL без подписи
    .session      = session,                           // 8 символов [0-9a-zA-Z], один на сессию
    .counter      = monotonic_ms,                      // не уменьшать в пределах session
});
defer gpa.free(url);

signedUrl возвращает error.UnsupportedPathCharacter, если в path есть символ, который OkHttp закодировал бы: в этом случае подписываемый (декодированный) путь и путь в URL различались бы, а такой сценарий для реальных id камер не нужен и не реализован.

12.5. Проектные решения

  • JPEG-превью вместо декодирования видео. Живой поток — H.264/H.265; декодера на чистом Zig нет, а FFmpeg ради первой картинки — лишняя зависимость. live_preview отдаёт JPEG, который Windows декодирует сама. Это несколько кадров в секунду, не полноценное видео.
  • Полноценное видео — внешним плеером. Приложение Ivideon поступает так же: строит подписанный URL и отдаёт строку плееру на FFmpeg. Команда url даёт ту же строку.
  • Только std и системные DLL. Сборка одной командой, без менеджера пакетов.
  • Секреты. Пароль не хранится и не печатается; токен — в локальном файле, который должен попасть в .gitignore; URL с токеном выводится только по явной команде url.

12.6. Где вероятнее всего сломается при первом запуске

  1. TLS. std.http.Client использует собственную реализацию TLS из Zig std; совместимость с серверами Ivideon (набор шифров, цепочка сертификатов) не проверена.
  2. Редирект на региональный хост. api.ivideon.com отвечает редиректом на eu01-api.ivideon.com (проверено для корня). POST с телом при 301/302 многие клиенты превращают в GET — редирект логина надо обрабатывать вручную, повторяя тот же POST на Location. После входа все запросы идут сразу на https://{api_host} из токена, и проблема исчезает.
  3. Форма ответа /servers?op=FIND. Метод помечен @kr7 — приложение получает «сырой» JSON и разбирает его вручную, поэтому структура известна хуже, чем у типизированных ответов. См. 06-api-reference.md.
  4. 2FA. Если на аккаунте включена двухфакторная авторизация, придёт токен с limited_to_2fa: true. Первая версия должна это распознать и сообщить, а не падать. См. 03-auth.md.
  5. Content-Type у live_preview. Ожидается image/jpeg; не проверено.

12.7. Порядок работы

  1. Zig 0.16.0 в tools/zig — сделано.
  2. Каркас CLI + sign.zig с тестами — sign.zig готов, CLI нет.
  3. login → cameras → snapshot, url — первая живая проверка протокола; запускает пользователь со своим аккаунтом.
  4. watch — окно просмотра.
